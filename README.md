# Life OS

Персональная система управления жизнью, построенная на Angular и Nx. Проект организован как монорепозиторий с разделением на доменную модель, прикладную логику, UI-функциональность и слой локального хранения данных.

## Технологический стек

- **Angular** — frontend-приложение.
- **Nx** — управление монорепозиторием, проектами и задачами.
- **TypeScript** — типизация и разработка.
- **ESLint** — статический анализ кода и контроль архитектурных границ.
- **SCSS** — стилизация интерфейса.
- **Dexie** — работа с IndexedDB для локального хранения данных.

## Архитектура

Проект использует разделение ответственности по слоям. Каждый слой решает собственную задачу и имеет ограничения на зависимости от других внутренних проектов.

### `domain-items`

**Тег:** `type:domain`

Содержит предметную область приложения:

- доменные сущности и типы;
- бизнес-правила и инварианты;
- интерфейсы и контракты, необходимые другим слоям.

Доменный слой не зависит от других внутренних проектов. Он не должен содержать Angular-компоненты, обращения к браузерному хранилищу или инфраструктурную реализацию.

### `application-items`

**Тег:** `type:application`

Содержит прикладную логику и сценарии использования:

- координацию бизнес-операций;
- use cases;
- взаимодействие с доменными моделями и контрактами;
- правила выполнения прикладных сценариев.

Слой зависит от `domain-items`, но не от UI и конкретных реализаций хранения данных.

### `feature-items`

**Тег:** `type:feature`

Содержит пользовательскую функциональность на Angular:

- компоненты и представления;
- пользовательские сценарии;
- координацию UI;
- взаимодействие с прикладными сценариями.

Слой может зависеть от `application-items` и `domain-items`. Бизнес-правила не должны дублироваться в компонентах.

### `data-access-local`

**Тег:** `type:data-access`

Отвечает за локальное хранение и доступ к данным:

- работу с IndexedDB;
- интеграцию с Dexie;
- реализацию контрактов доменного слоя;
- преобразование данных между формами хранения и моделями приложения, если это необходимо.

Слой может зависеть от `domain-items`, но не должен зависеть от UI или прикладного слоя. Это позволяет менять реализацию хранения без переноса инфраструктурных деталей в бизнес-логику.

### `shared-ui`

**Тег:** `type:ui`

Содержит переиспользуемые UI-компоненты и элементы интерфейса:

- общие визуальные компоненты;
- отображение состояний интерфейса (ошибка, пустое состояние, разработка);
- переиспользуемые элементы форм и управления;
- общие UI-шаблоны и стили;
- интеграцию с Angular и UI-библиотеками, например Taiga UI.

Библиотека не содержит бизнес-логики и не зависит от конкретных feature-модулей. Её компоненты могут использоваться в разных частях приложения.

### `life-os`

**Тег:** `type:app`

Корневое Angular-приложение и точка композиции системы:

- инициализация приложения;
- настройка маршрутизации;
- подключение функциональных модулей и standalone-компонентов;
- конфигурация DI;
- связывание прикладных контрактов с конкретными реализациями инфраструктуры.

Приложение может использовать все внутренние слои и отвечает за их интеграцию.

## Правила зависимостей

Архитектурные границы проверяются правилом `@nx/enforce-module-boundaries` из Nx ESLint Plugin.

| Исходный слой      | Разрешённые внутренние зависимости                                                           |
| ------------------ | -------------------------------------------------------------------------------------------- |
| `type:domain`      | Нет                                                                                          |
| `type:application` | `type:domain`                                                                                |
| `type:data-access` | `type:domain`                                                                                |
| `type:ui`          | `type:ui`                                                                                    |
| `type:feature`     | `type:ui`, `type:application`, `type:domain`                                                 |
| `type:app`         | `type:app`, `type:feature`, `type:ui`, `type:application`, `type:domain`, `type:data-access` |

Эти ограничения относятся к зависимостям между внутренними проектами Nx. Импорты внешних npm-пакетов регулируются другими правилами и требованиями проекта.

### Основные принципы

1. **Зависимости направлены внутрь.** Доменная логика не зависит от инфраструктуры и UI.
2. **Прикладная логика не зависит от конкретного хранения.** Она использует контракты, а не реализацию Dexie.
3. **Инфраструктура реализует контракты.** Конкретное хранилище подключается на уровне композиции приложения.
4. **UI не владеет бизнес-правилами.** Компоненты отвечают за представление и взаимодействие с пользователем.
5. **Изменения не должны обходить архитектурные границы.** Если новая функциональность требует запрещённой зависимости, следует пересмотреть расположение кода или контракт между слоями.

## Разработка

### Требования

- Node.js — версия, совместимая с текущими зависимостями проекта.
- npm.
- Git.

### Установка зависимостей

```bash
npm install
```

### Запуск приложения

```bash
npx nx serve life-os
```

### Production-сборка

```bash
npx nx build life-os
```

### Проверка линтинга

```bash
npx nx run-many -t lint
```

Для принудительного повторного выполнения задач без использования кеша Nx:

```bash
npx nx run-many -t lint \ --skip-nx-cache
```

### Проверка TypeScript-библиотек

Для библиотек, у которых настроен `build` через `tsc --noEmit`:

```bash
npx nx run domain-items:build
npx nx run application-items:build
npx nx run data-access-local:build
```

Эти задачи проверяют TypeScript без генерации сборочных артефактов.

### Просмотр проектов Nx

```bash
npx nx show projects
```

Просмотр конфигурации конкретного проекта:

```bash
npx nx show project life-os --json
```

## Добавление функциональности

При разработке новой функциональности сначала определите её ответственность:

1. **Предметные понятия и бизнес-инварианты** размещайте в `domain-items`.
2. **Сценарии использования и координацию операций** размещайте в `application-items`.
3. **Пользовательские интерфейсы и взаимодействия** размещайте в `feature-items`.
4. **Работу с IndexedDB и другими деталями хранения** размещайте в `data-access-local`.
5. **Маршрутизацию, конфигурацию DI и связывание реализаций** размещайте в `apps/life-os`.

Не создавайте новую библиотеку только ради дополнительного уровня абстракции. Выделение в отдельный Nx-проект должно оправдываться самостоятельной ответственностью, повторным использованием или необходимостью обеспечить архитектурные ограничения.

## Статус архитектуры

На текущем этапе настроены основные Nx-проекты, их теги и проверки ESLint. Линтинг проектов проходит успешно.

При этом успешный линтинг сам по себе не подтверждает наличие тестов, полноценной production-сборки каждой библиотеки или корректность всех runtime-зависимостей. Эти проверки следует добавлять по мере реализации функциональности.
